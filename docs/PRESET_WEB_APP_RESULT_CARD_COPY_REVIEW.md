# PRESET_WEB_APP_RESULT_CARD_COPY_REVIEW

Use this when the first `web-app` proof already shows one visible result card and you want a fast wording review before widening scope.

## Goal

Keep the first result card believable, specific, and aligned with the landing-page proof.

## Fast review

1. The card headline names one concrete outcome, not a whole launch claim.
2. The supporting copy explains what input produced the card.
3. The card does not imply hidden dashboards, extra screens, or completed integrations.
4. The same proof still appears in `docs/landing-page-brief.md`, `docs/information-architecture.md`, and `demo/run_demo.sh`.
5. If the copy sounds broader than the visible UI proof, trim the wording before adding more features.

## Pass cue

The first card reads like one honest proof artifact from one form submission.
